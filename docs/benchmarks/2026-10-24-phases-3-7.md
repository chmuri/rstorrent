# Scalability phases 3-7 — measured results (2026-10-24)

Same host and harness as `2026-10-24-scaling.md`: 8 cores, ext4, release
build, 14,000 synthetic paused torrents, no payload, no trackers. Treat the
absolute numbers as directional and the ratios as the artifact.

## Cumulative effect at 14k

| Metric | pre-index | after index | final (phases 3-7) |
|---|---:|---:|---:|
| startup `full_s` | 157.90 | 1.375 | **0.918** |
| peak RSS | 129.7 MB | 134.3 MB | 143.8 MB |
| `d.hash` p99 | 1.038 ms | 0.165 ms | 0.184 ms |
| `d.multicall2` p50 (12 cols) | 47,096 ms | 217 ms | **202 ms** |

Startup improved a further ~33% from parallel session parsing; lookup and
multicall are flat within run-to-run noise. The peak RSS delta (+9 MB) is the
extra loader threads, pool worker, and per-download index maps.

## Rechecks — 8 torrents x 64 MiB

| | `storage.disk_threads=1` | `storage.disk_threads=4` |
|---|---:|---:|
| `d.check_hash` trigger (8 calls) | 3.9 ms | 3.1 ms |
| wall | 5.21 s | 2.63 s |
| throughput | 103 MB/s | 204 MB/s |
| peak concurrent passes | 4 | 4 |
| process threads | 15 | 15 |

Two caveats:

- `d.check_hash` used to run the pass inline on the RPC thread (the old code
  wrapped it in a per-call thread). It now queues on the bounded hash
  scheduler, so triggering 8 passes costs ~3 ms regardless of payload size.
- The 2x wall difference between the two runs is **cache warmth, not worker
  count**: hash reads bypass the disk worker, so `storage.disk_threads` does
  not change hashing throughput. Concurrent passes are bounded by
  `storage.hash_concurrency` (4 by default), which is why peak threads is 15
  in both runs.

## Disk pool write throughput

`cargo test -p lt-storage --test test_disk_pool_throughput -- --ignored --nocapture`
(debug build, 4 torrents x 64 MiB, each 1 MiB piece written through its shard):

```
1 worker:  0.50 s (537 MB/s)
4 workers: 0.31 s (870 MB/s)  -> 1.62x
```

Debug-build numbers; a release build should scale further until the device
saturates. The test also verifies every byte of every payload, so a speedup
cannot come from dropped or interleaved writes.

## What each change contributed

| Change | Evidence |
|---|---|
| Bounded hash scheduler | trigger latency 5.9 s -> 3 ms for 8 passes; thread count stops tracking recheck count |
| Parallel session parse | startup 1.375 s -> 0.918 s |
| Sharded disk pool | 1.62x write throughput at 4 workers; shard isolation and shutdown-drain tests |
| One sync per pass | 3 syncs -> 1 for a 3-piece pass, with pre-queued writes still visible |
| Multicall parse hoisting | 225 ms -> 178 ms p50 at 14k x 12 (run-to-run up to ~202 ms) |

## Reproduce

```bash
scripts/bench/run_all.sh --count 14000 --lookups 1000 --multicall 5 --threads 4
scripts/bench/run_all.sh --count 1000 --recheck-count 8 --recheck-mb 64 --threads 4
```
