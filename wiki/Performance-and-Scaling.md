# Performance and scaling

`rstorrent` is built to stay responsive with large sessions. The numbers below
were measured on an 8-core host with a local ext4 volume, using a synthetic
session generated by [`scripts/bench`](https://github.com/chmuri/rstorrent/tree/main/scripts/bench).

## Measured at 14,000 torrents

| Metric | Result |
|---|---:|
| Restore to fully loaded | ~0.9–1.2 s |
| RSS | ~145 MB (~10 KB/torrent) |
| `d.hash` p99 | ~0.2 ms |
| `d.multicall2`, 12 columns, p50 | ~0.2 s |
| Recheck trigger (`d.check_hash`) | ~3 ms, queued |

Before the 0.14.0 work, the same machine took **158 seconds** to restore 14,000
torrents and **47 seconds** for one multicall poll. The improvement is
algorithmic, not just micro-optimisation.

## Why it scales

- **Hash-indexed lookups.** `DownloadList` and every view keep a hash→position
  map beside their ordered vector, so lookups and duplicate checks are O(1)
  without changing view ordering.
- **Parallel session restore.** Torrent, sidecar and resume files are parsed on
  a bounded thread pool, then inserted in their original order so events and
  views remain deterministic.
- **Bounded rechecks.** Hash passes run on a fixed pool with a FIFO queue. One
  torrent still hashes on one thread, but a thousand queued rechecks no longer
  create a thousand threads, and the RPC call returns immediately.
- **Sharded disk I/O.** Each torrent is assigned a disk worker by the first four
  bytes of its info hash. All of that torrent's reads, writes, syncs and hash
  flush use the same worker, preserving per-torrent ordering; unrelated
  torrents proceed in parallel.
- **One flush per hash pass.** During verification the engine already blocks new
  writes for the torrent, so the pass needs a single flush before its first read
  instead of one per piece.

## Settings

All values are read at startup; restart to apply changes.

| Setting | Default | Range | Purpose |
|---|---:|---:|---|
| `storage.disk_threads` | cores ÷ 2, clamped 2–16 (fallback 4) | 1–64 | Disk workers. Raise for concurrent I/O across torrents. |
| `storage.max_open_files` | 64 | 4–65536 | Per-worker open-file cache. |
| `storage.hash_concurrency` | min(4, cores) | 1–1024 | Concurrent hash passes. |
| `storage.load_threads` | min(4, cores) | 1–64 | Session parsing during startup. |
| `storage.hash_read_cache` | 64 | 64–1024 | Files a single hash pass keeps open. |

Example for a dedicated NVMe machine:

```ini
storage.disk_threads = 4
storage.max_open_files = 128
storage.hash_concurrency = 4
```

## Caveats

- **Hash throughput follows `storage.hash_concurrency`, not
  `storage.disk_threads`.** Hash reads bypass the disk worker by design; the
  disk pool helps writes, reads, syncs and concurrent torrents.
- **FUSE and union mounts (`shfs`) are a single bottleneck.** More workers do
  not scale past the mount's serialisation. Benchmark a direct mount separately.
- **`storage.disk_threads` defaults to half the detected core count** (clamped
  to 2–16, fallback 4). Set it explicitly to pin the worker count; the
  per-torrent sharding invariant makes any value safe, and it is covered by
  bitfield-equality and per-shard write tests.
- **Descriptor budget.** Keep `threads × max_open_files` below about a third of
  `RLIMIT_NOFILE`; each concurrent hash pass also opens up to
  `storage.hash_read_cache` files outside the worker cache.

## Reproducing

```bash
# Startup, lookup and multicall on a synthetic 14k session
scripts/bench/run_all.sh --count 14000

# Recheck behaviour with a payload session
scripts/bench/run_all.sh --count 1000 --recheck-count 100 --recheck-mb 32 --threads 4

# Disk-pool write throughput
cargo test -p lt-storage --test test_disk_pool_throughput -- --ignored --nocapture
```

See [`docs/scalability.md`](https://github.com/chmuri/rstorrent/blob/main/docs/scalability.md)
for the full thread model, invariants and descriptor accounting.
